# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Bare-metal STM32 firmware that drives a **VGA monitor** from an STM32F767ZI (Nucleo-144) using the **LTDC** peripheral. The LTDC generates standard 640x480@60 VGA timing; RGB output is taken from only the **top bits of each color channel** through an external resistor DAC, so the usable palette is 8 colors. Comments in `Core/Src/main.c` and `docs/` are in Thai.

This board is the **Tetris "Hub"**: a C port of the `../mad-python-uart-simulation` PC Hub simulator. It receives game packets (JOIN/STATE/ATTACK/…) from a separate STM32 **Logic** board over UART, runs the lobby/match state machine, replies (START/RESULT/ATTACK_TX), and renders the whole game on the VGA screen. See `docs/system-architecture.md` for the full RFID→ESP32→Logic→Hub→screen chain.

- MCU: STM32F767ZITx, Cortex-M7, 216 MHz (HSE bypass 8 MHz → PLL).
- Generated by STM32CubeMX; `mad-stm32-tetris-VGA.ioc` is the source of truth for pinout/clocks.
- CubeMX-enabled peripherals: CORTEX_M7, LTDC, NVIC, RCC, SYS. **UART is NOT in the `.ioc`** — USART6 is configured at register level in `main.c` (no HAL UART driver in the project).

## Build

Toolchain: GNU Tools for STM32 (arm-none-eabi-gcc 14.3.rel1), normally via STM32CubeIDE. The toolchain is **not on PATH**; for a CLI build prepend it:

```sh
export PATH="/Applications/STM32CubeIDE.app/Contents/Eclipse/plugins/com.st.stm32cube.ide.mcu.externaltools.gnu-tools-for-stm32.14.3.rel1.macosaarch64_1.0.0.202602081740/tools/bin:$PATH"
make -C Debug all      # produces Debug/mad-stm32-tetris-VGA.elf
make -C Debug clean
```

`Debug/makefile` and the `*.mk`/`subdir.mk` files are **auto-generated by the IDE — do not hand-edit them** (they are regenerated on reopen/build). Regenerate by editing `mad-stm32-tetris-VGA.ioc` in CubeMX/CubeIDE or by changing sources.

**Adding a new source file/folder for CLI `make`** (the IDE does this automatically, but a bare `make` won't): the linker reads `@Debug/objects.list`, **not** the `OBJS` in the `.mk` files — forgetting to add the `.o` there gives "undefined reference" + "Unknown destination type (ARM/Thumb)" at link even though the `.o` exists. Also update `Debug/Core/<folder>/subdir.mk`, `Debug/makefile` (`-include`), and `Debug/sources.mk` (`SUBDIRS`), and add `-I../Core/<folder>` to **every** subdir.mk compile rule.

Host-test the portable logic (no HAL deps) with native cc:

```sh
cc -std=gnu11 -I Core/Inc runtests.c Core/protocol/proto.c Core/hub/hub.c Core/tests/hub_test.c
```

Linker script: `STM32F767ZITX_FLASH.ld` (flash target) / `STM32F767ZITX_RAM.ld`. Links with `--specs=nano.specs --specs=nosys.specs`, hard float (`fpv5-d16`).

Flash/debug: `mad-stm32-tetris-VGA.launch` (ST-LINK / OpenOCD via CubeIDE).

## Layout

CubeMX files live in `Core/Src` + `Core/Inc`; hand-written Hub code lives in per-feature folders directly under `Core/` (headers kept beside their `.c`):

- `Core/Src/main.c` — entry point, `SystemClock_Config`, `MPU_Config`, VGA app (`VGA_Start`, `VGA_Pixel`), the register-level USART6 driver + ISR + ring buffer, and the main loop that wires UART → parser → hub → render.
- `Core/protocol/proto.c` — port of `protocol.py`: CRC-8/SMBUS, packet build/parse, byte-level `proto_parser_feed_byte`. Wire bytes verified identical to the Python `protocol.md`.
- `Core/hub/hub.c` — port of `hub_sim.py`: lobby/match state machine (`hub_init/handle/update`) + `DebugStats`. Time base is **ms (HAL_GetTick)**, not float seconds.
- `Core/display/vga_draw.c` + `font5x7.h` — port of `render.py`: `vga_render`. Only 8 colors, so the palette is approximated (L piece→yellow, garbage→white, grey→blue).
- `Core/tests/hub_test.c` — port of the Python self-tests: `hub_selftest()`, `hub_lobby_tests()` (20 checks), and `fake_board_*` which drives the Hub with a synthetic game so the screen demos with no hardware attached.
- `Core/Src/ltdc.c` — `MX_LTDC_Init` (VGA timing) + `HAL_LTDC_MspInit` (LTDC pin mux, PLLSAI clock).
- `Core/Src/gpio.c` — `MX_GPIO_Init`. `stm32f7xx_it.c` — interrupt handlers. `stm32f7xx_hal_msp.c` — HAL MSP.
- `Core/Startup/startup_stm32f767zitx.s` — vector table / reset. `Drivers/` — vendor HAL/CMSIS (do not modify).
- `docs/` — wiring + architecture notes (Thai): `system-architecture.md`, `uart-wiring.md`, `uart-firmware-integration.md`, `vga-wiring.md`.

## Editing rules

- **CubeMX round-trip:** CubeMX regenerates `Core/Src/*.c` and `ltdc.c`/`gpio.c` on `.ioc` changes. Put hand-written code **only between `/* USER CODE BEGIN x */` and `/* USER CODE END x */` markers** — anything outside is overwritten. The VGA code lives in `USER CODE BEGIN 2`, `USER CODE BEGIN 4`, and `PV`.
- Don't edit files under `Drivers/` or the auto-generated `Debug/` build files.

## How the display works (key facts)

- Framebuffer: `uint8_t framebuffer[640*480]` in `main.c`, 32-byte aligned, **L8 (8bpp indexed)** pixel format.
- CLUT maps index→color using only bits 2/1/0 → R/G/B (8 colors), matching the resistor-ladder wiring (top bit per channel).
- `MX_LTDC_Init` sets the 640x480 VGA timing; `VGA_Start` reconfigures layer 0 to L8 + the framebuffer and loads the CLUT. Note `main.c` sets layer 0 up again after `ltdc.c` configured two ARGB8888 layers.
- Pixel clock derives from PLLSAI (set in `HAL_LTDC_MspInit`, ~25.2 MHz target for VGA).
- `MPU_Config` runs before `HAL_Init`.

## Runtime / UART (main loop)

- **USART6 on PG14 (TX) / PG9 (RX), AF8, 921600 8N1**, register-level (APB2 clock → `BRR = PCLK2/baud`). RX via `USART6_IRQHandler` → `rx_ring[]`; the main loop drains the ring into `proto_parser_feed_byte`. `uart_send` is a blocking TX used as the Hub's reply callback.
- Loop order each iteration: drain RX → `hub_update` (time-based lobby) → read B1 → render at ~30 fps (every 33 ms). **B1 (PC13)** toggles the debug panel (`g_show_debug`); **PB7 LED** is a UART-RX activity indicator (lit ~150 ms after each byte), *not* a liveness blink.
- Boot path (`USER CODE BEGIN 2`): `VGA_Start` → `USART6_Init(921600)` → `proto_parser_init` → `hub_init` → `hub_seed_rng`. When no real packet arrives for a while, `fake_board_*` demos the game on screen.
